# Локальная проверка Studio без управления окнами

`studio_qa.py` использует встроенный Studio MCP через stdio. Зависимости:
Python 3.9+, локальная Roblox Studio с включённым MCP и уже открытая тестовая
копия проекта. Пакеты pip и облачные ключи не требуются.
Процессу нужен доступ к локальной сети: Studio подключается к proxy через
localhost. Запуск внутри песочницы с запрещённой сетью может вернуть пустой
список сцен, хотя окно Studio открыто. Инструмент ждёт регистрацию до 30 с,
но сам не меняет разрешения сети и не перезапускает редактор.

## Фоновые снимки

Сценарий `journal` также сверяет состав фабрики (13 кафе / 25 стажёров в
тестовом профиле), награду и длительность цикла с серверным снимком, затем
проверяет пустую фабрику и временный ready=false. Открывает дневник в прогулке,
проверяет остановку движения и подсказок, конфликт с каталогом/посещениями,
возврат управления и сохранение текущего ручного разреза. `layout` проверяет подписи
журнала в узкой панели на русском и английском. Это проверка размеров и
TextFits; визуальный осмотр требует отдельного снимка.

На macOS можно собрать тестовую сцену, дождаться новых кадров и снять только
её окно через ScreenCaptureKit:

```sh
python3 tools/studio_qa.py capture --scene cutting --image /tmp/cut-review.png --report /tmp/cut-review.json
```

Сцены: `cutting`, `kitchen`, `rear`, `catalog`. В `rear` тест расширяет поле
зрения до 90 градусов, чтобы задний кабинет помещался в широком окне Studio;
рабочая камера игры не меняется. Реальные размеры viewport и поле зрения
записываются в отчёт. PNG содержит окно Studio целиком, включая панели редактора.

Нужны установленные Swift command line tools и уже выданное macOS-разрешение
записи экрана. Команда сама не запрашивает разрешения, не активирует окна, не
переключает рабочие столы и не делает снимок всего экрана. Она требует ровно
одно окно Studio с именем выбранного тестового place. В отчёте сохраняются
идентификатор окна и активное приложение до/после захвата; смена активного
приложения самим пользователем не означает, что инструмент забрал фокус.

Путь PNG должен быть новым: существующий файл не перезаписывается. Отказ
доступа, отсутствие свежих кадров или ошибка захвата дают ненулевой код.
Даже при ошибке принадлежащий проверке Play останавливается, исходники
восстанавливаются. Блокировку экрана инструмент не снимает. Успешное сохранение
PNG означает готовность к осмотру, а не подтверждение правильности картинки:
агент должен открыть изображение и оценить его отдельно.

## Подготовка

Собрать текущий проект:

```sh
rojo build -o /tmp/infinite-chocolatier-qa.rbxlx
```

Один раз открыть эту копию в Studio, включить её MCP и оставить Edit.
Инструмент сам не открывает окна, не переключает рабочие столы и не запускает
Roblox Player. Для существующей копии `chocolatier-diagnostics.rbxlx` имя можно
не указывать; для новой использовать `--place-name infinite-chocolatier-qa.rbxlx`.
Рабочую опубликованную сцену инструмент отвергает по PlaceId и имени.

## Команды

```sh
python3 tools/studio_qa.py list
python3 tools/studio_qa.py check
python3 tools/studio_qa.py sync
python3 tools/studio_qa.py smoke
python3 tools/studio_qa.py gestures
```

`list` читает список подключённых редакторов. `check` проверяет, что выбранная
копия локальная, не запущена и содержит дерево нашего проекта. `sync` обновляет
44 исходника (число вычисляется по src), добавляет новые модули и проверяет
прочитанный обратно Source. Неизвестный оставшийся скрипт считается ошибкой:
пересобрать копию через Rojo, а не молча удалять чужое содержимое.

`smoke` временно добавляет тестовый профиль и обработчик в памяти Studio,
запускает Play и проверяет:

- загрузку профиля с 12 кафе и 25 стажёрами;
- реальную серверную покупку craft ×10 и изменение дохода;
- четыре завершённых раунда и переход к следующему заказу;
- открытие/закрытие дневника и наличие офлайн-отчёта;
- русский и английский текст в панели 336 px, отсутствие наложения кнопок;
- домашнего стажёра и шесть подробных станций в очереди кафе;
- видимость новых деталей, перемещения и исключение дальней очереди из обхода;
- покупку и снятие часов, счётчик коллекции, сохранение бонуса и текст всех
  семи разделов каталога на русском и английском;
- отсутствие MessageError в журналах клиента и сервера.

Дополнительно проверяется доставка позы видимого соседа: настоящий KitchenRelay
получает условного автора на расстоянии 256 studs, строит подписку по CafeQueue
и отправляет позу настоящим RemoteEvent в клиент. Дальние неанимированные
комнаты исключаются отдельными Lune-тестами. Это проверка сетевого канала с
тестовым автором, не многопользовательский сеанс с двумя реальными людьми.

`idleNetwork` считает вызовы настоящего отправителя поз на копии view: 21
неподвижный отсчёт по 0.1 секунды, затем десять изменённых положений. Редкий
повтор допускается, движения должны отправиться все. Подменён только выход
в сеть счётчиком; живой разрез и экономика не изменяются.

`loadingRecovery` передаёт настоящим UI-обработчикам неполный `ready=false`,
затем сохранённый готовый снимок тестового профиля. Проверяет первый ответ,
несколько восстановлений, блокировку ввода/действий и возврат карточки заказа.
Сетевую задержку DataStore он не создаёт и к реальным сохранениям не обращается.

`avatarLifecycle` меняет назначение сразу после создания станции, а вторую
станцию удаляет до загрузки. Настоящий загрузчик должен собрать ровно один
R6-персонаж; проверяются масштаб, скрытие/возврат и удаление. Отрицательный
тестовый id использует запасную внешность без обращения к аккаунту. Поздние
ответы друга и повтор после ошибки проверяются управляемыми Lune-сценариями,
не выдаются за живой вход друга на сервер.

`apprenticeTempo` покупает один уровень скорости через сервер и ждёт новый
атрибут домашней комнаты. На отдельных часах того же контроллера проверяет
сохранение фазы, затем ускорение следующего шага. Настоящая станция получает
обе позы: положение ножа в момент изменения должно совпасть. Время в этой
проверке управляемое; это проверка геометрии, не плавности кадров на экране.

`rosterRefresh` временно меняет клиентский атрибут списка стажёров тестовой
комнаты. Только выдуманный QA-id собирается как обычный R6 без запроса аккаунта.
Проверяются замена одного персонажа, сохранение очереди, всех восьми станций и
прежних объектов стен/мебели. Другие назначения не меняются. Исходный атрибут
и загрузчик возвращаются даже при ошибке; настоящий вход друга не имитируется.

`peerReplacement` создаёт одну клиентскую соседнюю комнату с отрицательным
тестовым владельцем. Открывает настоящий режим наблюдения, заменяет модель с
тем же ключом, затем меняет её координаты. Проверяются новые ссылки/позиции,
удаление старой геометрии и закрытие прежнего наблюдения. Временная комната
удаляется при любом результате; это не второй подключённый игрок.

`directoryRefresh` создаёт восемь временных записей посетителей на клиенте.
Меняет имя и размер фабрики, закрывает/открывает меню, убирает и возвращает
одного владельца. Проверяются сохранение карточек и прокрутки, актуальность
подписей и создание только одной новой строки при возвращении. Отрицательные
QA-id не изображают настоящих подключённых игроков; поздние ответы портретов
и повтор неготовой картинки проверяются отдельно управляемыми Lune-сценариями.
Временные модели удаляются при любом результате.

`storageReceipt` исполняет настоящий ProfileStore на сервере Studio с таблицей
в памяти вместо DataStore. Ответ первой успешной записи теряется, повтор
должен восстановить исходный офлайн-отчёт без повторного начисления. Следующий
обычный claim уже возвращает нулевой новый отчёт. Реальные сохранения и
сетевые сбои Roblox не затрагиваются; повтор callback и незаписанная попытка
дополнительно проверяются Lune-тестами.

`publicDecor` проверяет установленную мебель в физической комнате условного
соседа и её подробной копии в очереди. Смена часов и удаление растения должны
сохранить станции и оболочки; выход хозяина не убирает декор перед оставшимся
гостем. Временная клиентская модель удаляется после проверки. Сценарий `catalog`
отдельно покупает/скрывает реальные часы тестового профиля и проверяет серверный
атрибут CafeAppearance. Это не сеанс с двумя настоящими игроками.

`gestures` — отдельный сценарий нативной мыши: четыре разреза, перемещение
большого куска, перемещение полоски и подтверждение ровно одного нового раунда
сервером. Координаты берутся из проекции игры. Обработчик только читает этапы
и геометрию; завершение разреза и отправка награды остаются за обычным Game.
Перед вводом проверяются RenderStepped, размер viewport, границы координат и
отсутствие перекрывающего интерфейса. Жест, после которого этап не изменился,
не повторяется автоматически.

Статус проверки 20 сентября: при заблокированном macOS камера возвращает
1×1, RenderStepped не приходит. Прямая проба user_mouse_input не завершилась
за два ожидания по 30 с; диагностическая сессия затем опознана и очищена
отдельно. Новый сценарий на том же Mac корректно отказывает **до** отправки
мыши и восстанавливает Edit. Положительный полный проход в работающем viewport
пока не подтверждён; переходы сценария покрыты изолированными Python-тестами.
Не объявлять этот режим успешно проверенным нативным вводом до живого прогона.
Обычный `smoke` доступен и без рендера.

После успеха, ошибки или обычного прерывания сценарий останавливает только
собственный Play, возвращает исходники из src и подтверждает Edit. Уже
запущенную сессию пользователя он не прерывает. Параллельный запуск второго
сценария запрещён блокировкой, которая освобождается ОС при выходе процесса.

При таймауте MCP повторная запись не отправляется: очистка сначала ждёт тот
же запрос. Если соединение не позволяет подтвердить восстановление, результат
остаётся неуспешным, а `cleanupError` сообщает об этом. При SIGKILL или падении
Studio автоматическая очистка не гарантируется: после возвращения в Edit
выполнить `sync`. В рабочем src тестовый обработчик никогда не появляется.

## Отчёт и границы проверки

Результат сохраняется в `/tmp/chocolatier-studio-report.json`, другой путь
задаётся через `--report`. Там находятся хеши исходников, этапы, результаты,
журнал Studio, подтверждение очистки и ограничения. Ошибка даёт ненулевой код
завершения. Сценарий не публикует игру и не обращается к настоящим сохранениям:
используется существующая ветка сервера `RunService:IsStudio()`.

Заблокированный macOS может не выполнять RenderStepped. Для проверки кухни
сценарий вызывает её настоящий обработчик кадров явно. Это не доказывает
правильность нативных жестов, плавность картинки или работу на реальном
телефоне. Проверка TextFits и координат не заменяет визуальную приёмку.
Снимки в этот сценарий не входят: известный розовый кадр native MCP и отказ
ScreenCaptureKit при блокировке не скрываются успешным статусом тестов.

Перед выпуском по-прежнему выполнять локально:

```sh
python3 -m unittest discover -s tests -p 'test_studio_qa.py'
lune run tests/run
rojo build -o /tmp/infinite-chocolatier-release.rbxlx
git --git-dir=.git-codex --work-tree=. diff --check
```

В GitHub Actions запускаются только обычные тесты Python/Lune и сборка.
Облачная Roblox Studio или облачные проверки движка не подключены.

`queueGrowth` строит отдельную тестовую очередь настоящим OnlineKitchen.
Переход 12 → 13 кафе должен сохранить шесть передних станций и их текущие
позы, заменить только две задние. Для 100 → 1 000 000 сравниваются количество
геометрии и идентичности комнат; смена Origin проверяет координаты станций
и удаление прежней очереди, 1 → 0 — освобождение старых моделей.
Запоздалая загрузка аватара не должна вернуть уничтоженную геометрию.
Тестовая копия атрибутов не меняет профиль, покупки или реальную комнату.
